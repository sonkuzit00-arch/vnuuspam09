# Обращения ДГД

Внутренний сервис учёта, маршрутизации и анализа обращений граждан. Заменяет
персональные Excel-файлы одним общим сервисом: карточка на обращение, личный
кабинет сотрудника (всё, что назначено ему — с любого канала) и живой общий
свод по всей команде.

## Стек

Next.js 14 (App Router) + TypeScript, Prisma + SQLite, NextAuth (Credentials),
Tailwind CSS + shadcn-style компоненты, framer-motion.

## Запуск

```bash
npm install
cp .env.example .env      # при необходимости поменяйте NEXTAUTH_SECRET
npx prisma migrate deploy
npm run db:seed           # демо-пользователи и примеры обращений
npm run dev
```

## Роли и маршрут обращения

1. Обращение регистрируется (любым сотрудником) и по умолчанию уходит в
   кабинет КАУ (Бабаханова Виктория).
2. Маршрутизировать обращение — назначить формат ответа (ДЗ, типовой ответ,
   типовой с разъяснением, перенаправление депутату/комитету и т.д.) и
   ответственного — может не только КАУ, но и любой администратор (Кузнецова,
   Астафьева): у обоих в кабинете есть раздел «Требуют маршрутизации» со
   всеми непромаршрутизированными обращениями, независимо от того, за кем
   они формально сейчас записаны.
3. Ответственный может либо передать обращение целиком другому человеку
   («Передать обращение» на карточке), либо, не передавая ответственность,
   поставить точечное поручение («Поручения» на карточке). Так моделируется
   реальный процесс согласования, например:
   - GR (Ковешникова) поручает ГД (Кузнецовой или Сибирко — смотря кто ведёт
     обращение) написать текст запроса;
   - автор запроса поручением направляет готовый текст на согласование
     обратно GR;
   - GR согласовывает и, если нужно, вносит правки (фиксирует как новую
     заметку/поручение);
   - тот же автор (Кузнецова или Сибирко) поручением направляет итоговый
     текст на согласование Чижову;
   - Чижов (роль «Согласующий») видит это поручение в своём кабинете и может
     только отметить его согласованным — никаких других действий в системе
     у него нет.
4. Вся цепочка — кто кому что поручил и в каком статусе — видна в общем
   своде в разделе «Кому как делегируются задачи» (КАУ/админы/согласующий/наблюдатель).

Роли: `ADMIN` и `KAU` — маршрутизируют обращения и назначают ответственных;
`GD` / `GR` / `OP` / `BTL_BF` — рабочие подразделения, видят только свой
кабинет; `APPROVER` — согласовывает только адресованные ему поручения;
`VIEWER` — только просмотр общего свода и отчётов, без единого действия.

## Деплой на внутреннем сервере (без публичного доступа)

Сервис рассчитан на закрытую внутреннюю сеть — наружу торчать не должен,
поэтому Railway/Vercel-style публичный хостинг не нужен. Два варианта:
Docker (проще для обновлений) или обычный systemd-процесс.

### Вариант 1 — Docker (рекомендуется)

```bash
cp .env.example .env
# впишите NEXTAUTH_SECRET (openssl rand -base64 32), NEXTAUTH_URL
# (адрес, по которому сервис будет виден внутри сети, напр. http://10.0.1.5:3000)
# и, по желанию, свой SEED_PASSWORD вместо demo1234
docker compose up -d --build
```

По умолчанию `docker-compose.yml` публикует порт только на `127.0.0.1` —
снаружи сервера сервис не виден. Чтобы открыть его коллегам по внутренней
сети, отредактируйте секцию `ports` в `docker-compose.yml` — либо укажите
там конкретный внутренний IP сервера (`10.0.1.5:3000:3000`), либо поставьте
перед контейнером внутренний nginx/reverse-proxy на LAN-интерфейсе. Данные
(SQLite) хранятся в именованном docker-volume `dgd_data` и переживают
пересборку образа.

### Вариант 2 — без Docker (systemd)

```bash
git clone <repo> /opt/dgd-appeals && cd /opt/dgd-appeals
npm ci
cp .env.example .env   # заполнить как выше, DATABASE_URL можно оставить file:./dev.db
npm run build
sudo cp deploy/dgd-appeals.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now dgd-appeals
```

Юнит сам выполняет `prisma migrate deploy && npm run db:seed && next start`
при каждом запуске (сидирование безопасно повторно — если обращения уже
есть, демо-данные не пересоздаются). По умолчанию Next.js слушает все
интерфейсы на порту 3000 — ограничьте доступ файрволом сервера до внутренней
подсети (`ufw`/`iptables`/группа безопасности), либо укажите конкретный
внутренний адрес через `HOSTNAME=10.0.1.5 npm run deploy:start`.

### Общее для обоих вариантов

- **Обязательно смените демо-пароль** (`demo1234`) перед реальным
  использованием — либо через `SEED_PASSWORD` до первого сидирования, либо
  сотрите базу и пересидите с новым паролем (пароль сейчас один на всех —
  индивидуальные пароли по пользователям можно добавить позже как отдельную
  задачу).
- `NEXTAUTH_SECRET` — обязателен и должен быть длинной случайной строкой,
  даже во внутренней сети (им подписываются сессии).
- Бэкап — это просто файл SQLite (`/data/dev.db` в Docker-volume или
  `prisma/dev.db` при systemd-варианте); регулярно копируйте его на другой
  носитель.

<details>
<summary>Альтернатива: облачный деплой с публичной ссылкой (Railway)</summary>

Если позже понадобится доступ извне (например, для демо), тот же образ можно
задеплоить на Railway — конфиг `railway.toml` уже в репозитории.

1. На [railway.app](https://railway.app) → **New Project** → **Deploy from GitHub repo**.
2. Добавить **Volume** (Settings → Volumes → New Volume, mount path `/data`) —
   иначе база будет стираться при каждом передеплое.
3. Задать переменные окружения: `DATABASE_URL=file:/data/dev.db`,
   `NEXTAUTH_SECRET` (случайная строка), `NEXTAUTH_URL` (домен, который
   выдаст Railway после первого деплоя — Settings → Networking).
4. Deploy — откроется публичная ссылка вида `https://<project>.up.railway.app/login`.

## Структура

- `src/app/(app)/page.tsx` — личный кабинет: обращения + поручения; для КАУ
  дополнительно раздел «Требуют маршрутизации»
- `src/app/(app)/appeals/new` — регистрация обращения (источник сгруппирован
  по подразделениям; для ГД — 4 канала: СЭД «Дело», почта, эл. почта,
  соцсети — с делением на личные сообщения и комментарии)
- `src/app/(app)/appeals/[id]` — карточка обращения: маршрут КАУ, концепция/
  алгоритм, поручения (цепочка делегирования), передача ответственного,
  история взаимодействия, благодарность/СМИ
- `src/app/(app)/summary` — общий свод + «Кому как делегируются задачи»
  (КАУ/админ/наблюдатель)
- `src/app/(app)/reports` — отчёты за период + экспорт в CSV (КАУ/админ/наблюдатель)
- `prisma/schema.prisma` — модель данных: `Appeal`, `AppealResponsible`
  (история передачи ответственного), `AppealTask` (поручения), `AppealEvent`
  (CRM-история)
- `prisma/seed.ts` — 9 реальных пользователей команды + демо-цепочка
  согласования (КАУ → GR → ГД → GR → ГД → согласующий)
- `Dockerfile`, `docker-compose.yml`, `deploy/dgd-appeals.service` — деплой
  на внутреннем сервере
