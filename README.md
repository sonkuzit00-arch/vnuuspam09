# Обращения ДГД

Внутренний сервис учёта, маршрутизации и анализа обращений граждан. Заменяет
персональные Excel-файлы одним общим сервисом: карточка на обращение, личный
кабинет сотрудника (всё, что назначено ему — с любого канала) и живой общий
свод по всей команде.

## Стек

Next.js 16 (App Router) + TypeScript, Prisma + PostgreSQL, NextAuth (Credentials),
Tailwind CSS + shadcn-style компоненты, framer-motion.

## Быстрый просмотр без установки

Откройте `preview/index.html` двойным щелчком — в браузере запустится
автономная демо-версия: все экраны (кабинет, карточка обращения с
поручениями и файлами, общий свод, отчёты с выгрузкой в Excel/CSV и
печатью в PDF, пользователи, профиль), вход под любым сотрудником.
Не нужны сервер, база и интернет; изменения сохраняются только в этом
браузере, кнопка «Сбросить демо-данные» на экране входа возвращает
исходное состояние. Уведомления и пароли в демо не работают.

## Роли и маршрут обращения

1. Обращение регистрируется — любым сотрудником, включая Кузнецову, Сибирко
   и Ковешникову, которые сразу ставят Бабаханову ответственной за
   распределение (это и есть значение по умолчанию в форме); но выбор
   ответственного в форме свободный — любой участник может сразу назначить
   любого ответственного, минуя очередь КАУ.
2. Маршрутизировать обращение — назначить формат ответа (ДЗ, типовой ответ,
   типовой с разъяснением, перенаправление депутату/комитету и т.д.) и
   ответственного — может не только КАУ, но и любой администратор (Кузнецова,
   Астафьева): у обоих в кабинете есть раздел «Требуют маршрутизации» со
   всеми непромаршрутизированными обращениями, независимо от того, за кем
   они формально сейчас записаны.
3. Ответственный может либо передать обращение целиком другому человеку
   («Передать обращение» на карточке), либо, не передавая ответственность,
   поставить точечное поручение («Поручения» на карточке). Так моделируется
   реальный процесс согласования, например:
   - GR (Ковешникова) поручает ГД (Кузнецовой или Сибирко — смотря кто ведёт
     обращение) написать текст запроса;
   - автор запроса поручением направляет готовый текст на согласование
     обратно GR;
   - GR согласовывает и, если нужно, вносит правки (фиксирует как новую
     заметку/поручение);
   - тот же автор (Кузнецова или Сибирко) поручением направляет итоговый
     текст на согласование Чижову;
   - Чижов (роль «Согласующий») видит это поручение в своём кабинете и может
     только отметить его согласованным — никаких других действий в системе
     у него нет.
   - Либо, короче: КАУ сама поручает Кузнецовой/Сибирко направить депутатский
     запрос без участия GR — тогда автор запроса поручением направляет его
     сразу на согласование Чижову, минуя шаг с Ковешниковой.
4. Вся цепочка — кто кому что поручил и в каком статусе — видна в общем
   своде в разделе «Кому как делегируются задачи» (КАУ/админы/согласующий/наблюдатель).

Роли: `ADMIN` и `KAU` — маршрутизируют обращения и назначают ответственных;
`GD` / `GR` / `OP` / `BTL_BF` — рабочие подразделения, видят только свой
кабинет; `APPROVER` — согласовывает только адресованные ему поручения;
`PRESS` — видит только обращения с отметкой «Освещено в СМИ»; `VIEWER` —
только просмотр общего свода и отчётов, без единого действия.

## Карточка обращения — поля регистрации

В блоке «Регистрация» на карточке: тема письма, дата поступления, номер
входящего в САДД, произвольное число исходящих номеров (перенаправления,
депутатские запросы — добавляются кнопкой «+»), для каждого — дата ответа
органа власти, краткая суть ответа и отметка «содействие оказано: да/нет»,
и отдельно номер ответа гражданину.

## Пользователи (администратор)

Раздел «Пользователи»: создать сотрудника (пароль генерируется или
задаётся вручную), сменить ФИО/email/роль, сбросить пароль, заблокировать
(история обращений сохраняется, войти нельзя). Каждый сотрудник может сам
сменить пароль в профиле.

Внизу страницы — «Удалить все обращения» (с подтверждением словом УДАЛИТЬ):
удаляет обращения, поручения, историю и файлы, пользователи остаются.
Демо-обращения при сборке больше не создаются; чтобы получить их на
тестовом стенде, задайте `SEED_DEMO_APPEALS=true`.

## Участники, которые не пользуются приложением

Если кто-то работает вне приложения (например, Чижов согласует по почте),
любой сотрудник с правом редактирования:
- в «Поручениях» отмечает поручение выполненным **за исполнителя** с указанием
  способа (по почте, по телефону, лично…) — в карточке видно, кто отметил;
  поручение можно «Вернуть в работу»;
- в блоке **«Ход согласования»** отмечает этапы: поступило от…, передано…,
  направлено на согласование, согласовано / с правками / не согласовано,
  получен ответ — кто, кому, когда, каким способом, комментарий. Любой этап
  можно исправить или удалить, все правки пишутся в историю.

Карточку (заявитель, контакты, канал, суть, описание, категория, ЦА) можно
исправить кнопкой «Редактировать карточку».

## Отчёты

Фильтры: период, ответственный, канал (или группа каналов — например,
«ГД; соцсети - комментарии» отдельно для отчёта в ЦУР). Выгрузка в
**Excel** (листы «По месяцам», «Положительные результаты», «Благодарности»,
«Все обращения»), **PDF** (по месяцам, положительные результаты,
благодарности) и CSV. Положительный результат — обращение решено или орган
власти по исходящему оказал содействие.

## Общий свод — аналитика

Помимо матрицы «источник × ответственный» и ленты поручений, общий свод
считает: среднее время на одно обращение (дней) и среднее число обращений
в день, динамику поступления по дням, результаты (решено/в работе/
просрочено) по каждому участнику лично и разбивку по группам каналов —
все каналы «ГД; …» объединяются в один хэштег «ГД» независимо от подканала,
как и требуется для количественно-качественного анализа.

## Каналы поступления

`ГД; САДД / «Дело»`, `ГД; почта`, `ГД; электронная почта`, `ГД; соцсети -
комментарии` (отдельно, для отчёта в ЦУР), `ГД; соцсети ДГД, личные
сообщения`, `приём и рабочие поездки`, `личные сообщения ДГД`, `общественные
приёмные (ОП)`, `сайт ОП (электронная форма)`, `КАУ`, `колл-центр`.

## Деплой на Vercel (с паролем на весь сайт)

1. [vercel.com](https://vercel.com) → **Add New → Project** → импортировать
   этот репозиторий. **Root Directory** оставить пустым, Production Branch —
   `main` (Settings → Environments → Production → Branch Tracking).
2. **Storage → Create Database → Neon (Postgres)** и подключить к проекту —
   `DATABASE_URL` пропишется автоматически.
3. **Settings → Environment Variables**:
   - `NEXTAUTH_SECRET` — случайная строка (`openssl rand -base64 32`);
   - `SITE_LOGIN`, `SITE_PASSWORD` — общий логин/пароль на вход на сайт
     (браузер спросит их до открытия любой страницы);
   - `SEED_PASSWORD` — пароль демо-пользователей вместо `demo1234`.
4. **Deploy**. Скрипт `vercel-build` сам применит миграции, засидит
   демо-данные (один раз) и соберёт проект.

Логин/пароль сайта в репозиторий не коммитятся — только в переменных
окружения Vercel. Без `SITE_LOGIN`/`SITE_PASSWORD` защита отключена.

### Файлы, уведомления, напоминания о сроках

- **Файлы к обращениям** — Storage → **Blob** → Create (тип *Private*) и
  подключить к проекту (`BLOB_READ_WRITE_TOKEN` пропишется сам). Файлы
  до 25 МБ, скачать их могут только вошедшие сотрудники. Без Blob (Docker,
  внутренний сервер) файлы до 10 МБ хранятся прямо в базе.
- **Почта** — `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`,
  `SMTP_FROM` (например, ящик на Яндекс/Mail.ru с паролем приложения).
- **Telegram** — создать бота у [@BotFather](https://t.me/BotFather), задать
  `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` (без @) и
  `TELEGRAM_WEBHOOK_SECRET` (случайная строка), передеплоить и нажать
  «Подключить вебхук бота» на странице «Пользователи».
- **Напоминания о сроках** — `CRON_SECRET` (случайная строка). Vercel Cron
  (`vercel.json`) раз в день в 09:00 МСК присылает напоминания о
  поручениях и контрольных сроках, истекающих в ближайшие сутки.

- **Выгрузка обращений на почту** — задайте `APPEALS_EMAIL_TO` (один или
  несколько адресов через запятую; нужны и SMTP-переменные выше). На этот
  ящик приходит копия каждого нового обращения со всеми полями и ссылкой на
  карточку, а в «Отчётах» появляется кнопка «На почту» — Excel-отчёт с
  текущими фильтрами уходит туда же.

- **Письма из почты → обращения** (Mail.ru, Яндекс, любой ящик с IMAP).
  Забираются только непрочитанные письма из папки `IMAP_FOLDER` (напр.
  `Обращения`). Каждое становится **черновиком на согласование**, который видит
  только проверяющий — `MAIL_IMPORT_RESPONSIBLE_EMAIL`, по умолчанию
  Кузнецова (`sofia@dgd.local`): раздел «Письма из почты на согласование» в
  кабинете. Проверяющий смотрит письмо и вложения, правит карточку
  («Редактировать карточку») и нажимает «Принять обращение» — оно появляется у
  КАУ в «Требуют маршрутизации» — или «Отклонить» (черновик удаляется).
  Письмо помечается прочитанным и повторно не импортируется; письма с адреса
  самого сайта пропускаются. Mail.ru: `IMAP_HOST=imap.mail.ru`, `IMAP_PORT=993`,
  `IMAP_USER` — адрес, `IMAP_PASSWORD` — пароль для внешних приложений.
  Забрать: кнопка «Забрать письма» в кабинете проверяющего; автоматически —
  Vercel Cron раз в сутки, чаще — через [cron-job.org](https://cron-job.org):
  GET `https://<сайт>/api/cron/mail-import` с заголовком
  `Authorization: Bearer <CRON_SECRET>`.

Каждый сотрудник сам включает почту и/или привязывает Telegram в разделе
**«Профиль и уведомления»**. Приходят: новое обращение или поручение на
вас, передача обращения вам, выполнение поручения, которое вы поставили,
и приближение сроков.

## Деплой на внутреннем сервере (без публичного доступа)

Альтернатива для закрытой внутренней сети — наружу не торчит,
если публичный хостинг (Vercel) не нужен. Два варианта:
Docker (проще для обновлений) или обычный systemd-процесс.

### Вариант 1 — Docker (рекомендуется)

```bash
cp .env.example .env
# впишите NEXTAUTH_SECRET (openssl rand -base64 32), NEXTAUTH_URL
# (адрес, по которому сервис будет виден внутри сети, напр. http://10.0.1.5:3000)
# и, по желанию, свой SEED_PASSWORD вместо demo1234
docker compose up -d --build
```

По умолчанию `docker-compose.yml` публикует порт только на `127.0.0.1` —
снаружи сервера сервис не виден. Чтобы открыть его коллегам по внутренней
сети, отредактируйте секцию `ports` в `docker-compose.yml` — либо укажите
там конкретный внутренний IP сервера (`10.0.1.5:3000:3000`), либо поставьте
перед контейнером внутренний nginx/reverse-proxy на LAN-интерфейсе. Данные
(PostgreSQL) хранятся в именованном docker-volume `dgd_pg` и переживают
пересборку образа.

### Вариант 2 — без Docker (systemd)

```bash
git clone <repo> /opt/dgd-appeals && cd /opt/dgd-appeals
npm ci
cp .env.example .env   # заполнить как выше, DATABASE_URL — локальный PostgreSQL
npm run build
sudo cp deploy/dgd-appeals.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now dgd-appeals
```

Юнит сам выполняет `prisma migrate deploy && npm run db:seed && next start`
при каждом запуске (сидирование безопасно повторно — если обращения уже
есть, демо-данные не пересоздаются). По умолчанию Next.js слушает все
интерфейсы на порту 3000 — ограничьте доступ файрволом сервера до внутренней
подсети (`ufw`/`iptables`/группа безопасности), либо укажите конкретный
внутренний адрес через `HOSTNAME=10.0.1.5 npm run deploy:start`.

### Общее для обоих вариантов

- **Обязательно смените демо-пароль** (`demo1234`) перед реальным
  использованием — либо через `SEED_PASSWORD` до первого сидирования, либо
  сотрите базу и пересидите с новым паролем (пароль сейчас один на всех —
  индивидуальные пароли по пользователям можно добавить позже как отдельную
  задачу).
- `NEXTAUTH_SECRET` — обязателен и должен быть длинной случайной строкой,
  даже во внутренней сети (им подписываются сессии).
- Бэкап — `pg_dump` базы (в Docker: `docker compose exec db pg_dump -U dgd dgd > backup.sql`);
  регулярно копируйте его на другой носитель.

## Структура

- `src/app/(app)/page.tsx` — личный кабинет: обращения + поручения; для КАУ
  дополнительно раздел «Требуют маршрутизации»
- `src/app/(app)/appeals/new` — регистрация обращения (источник сгруппирован
  по подразделениям; для ГД — 4 канала: СЭД «Дело», почта, эл. почта,
  соцсети — с делением на личные сообщения и комментарии)
- `src/app/(app)/appeals/[id]` — карточка обращения: маршрут КАУ, концепция/
  алгоритм, поручения (цепочка делегирования), передача ответственного,
  история взаимодействия, благодарность/СМИ
- `src/app/(app)/summary` — общий свод + «Кому как делегируются задачи»
  (КАУ/админ/наблюдатель)
- `src/app/(app)/reports` — отчёты за период + экспорт в CSV (КАУ/админ/наблюдатель)
- `prisma/schema.prisma` — модель данных: `Appeal`, `AppealResponsible`
  (история передачи ответственного), `AppealTask` (поручения), `AppealEvent`
  (CRM-история)
- `prisma/seed.ts` — 10 реальных пользователей команды + демо-цепочка
  согласования (КАУ → GR → ГД → GR → ГД → согласующий)
- `Dockerfile`, `docker-compose.yml`, `deploy/dgd-appeals.service` — деплой
  на внутреннем сервере
